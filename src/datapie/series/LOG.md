# Bug Log — `datapie/src/datapie/series`

Compiled with AI assistance while documenting this folder. I am new to the
codebase and have not tried to judge which findings are intentional design and
which are defects; everything observed is recorded, and a review from someone who
knows the module would be welcome.

Findings are anchored on method and function names, not line numbers. Items marked
*(observed)* were confirmed by running the package; everything else follows from
reading the code.

**Source changes.** Two, both outside the docstrings:

1. `_timing.py` — `redate` tested `old_data` while the parameter is `old_date`, so
   every call raised `NameError`. Typo corrected; the function now works in both
   modes.
2. `_uv_filters.py` — a `univariate_filters` method with a `pass` body was added to
   carry the documentation shared by the four filters. No filtering logic touched.

Everything else is docstrings plus `add_heading=False` on decorators that already
carried `@_dm.reference`.

**Files with no block:** `_categories.py` (a dict), `_functionalize.py` (a
template), `functions.py` (re-exports), `_views.py` (private `repr` machinery),
`_elementwise.py` and `_statistics.py` (51 names generated by `exec`, excluded by
decision). `series/_views.py` does **not** have the `_VERTICAL_ELLIPSIS` bug its
`databoxes/` counterpart has — it qualifies the constant in both places.
*(observed)*

## `_apply_to_variants.py`

### Bugs

1. **`_apply_to_variants` mutates before it validates.** `self.data =
   extended_data` and `self.start = extended_periods[0]` run before `func` is
   called; the type and shape checks fire after it returns. When `func` returns the
   wrong thing, the exception is raised on a series that has already been extended
   and re-dated. *(observed)*: a four-period series starting 2020Q1, given a `span`
   reaching back to 2019Q3 and a `func` returning a string, raised `TypeError` and
   left the caller holding a **six**-period series starting 2019Q3 with two leading
   missing values. A wrong-shape return does the same. Catching the exception does
   not undo it.
2. **NaN padding uses the series dtype.** The pad is built with
   `_np.full(..., _np.nan, dtype=self.data.dtype)`, so an integer-typed series
   cannot be extended. *(observed)*: an `int64` series given a wider span raised
   `ValueError: cannot convert float NaN to integer`, preceded by
   `RuntimeWarning: invalid value encountered in cast`.

### Notes

1. The `periods` argument is dead in all four kernels. `_apply_to_variants` builds
   `periods_tuple` and passes it; none of `_cum_avg`, `_exp_smooth`,
   `_double_exp_smooth`, `_decay_avg` reads it. The argument is correctly formed
   — *(observed)*, `func` receives periods and values of equal length — so this is
   unused machinery, not a defect.
2. `_create_extended_data_array` always copies, even when no padding is needed, so
   a caller cannot write through to the series' own data. *(observed)*
3. `_create_extended_data_array` never trims: `max(0, ...)` on both ends, so this
   path can only widen a series.

## `_broadcasts.py`

### Bugs

1. **`broadcast_variants_when_needed` mutates its second argument, and the two
   call sites differ.** In `_lays.py`, `overlay_by_span` passes a copy while
   `overlay_by_observation` passes `other` directly. *(observed)*

   `a.overlay_by_span(b)` left `b.num_variants` at 1. Same finding as `_lays.py`
   bug 1.

### Notes

1. `broadcast_variants(0)` is accepted and empties the series:
   `_np.repeat(data, 0, axis=1)` gives shape `(n, 0)` and `is_empty` becomes
   `True`. *(observed)* for all five combinations — 1→3 widens, 3→3 does nothing,
   3→2 and 3→1 raise, 1→0 empties. No caller passes zero, so this is a latent
   robustness gap. Negative counts were not tested.

## `_conversions.py`

### Bugs

1. **`select` never works.** `_aggregate_within_data` converts it to a tuple, which
   numpy reads as one index per dimension. Two or more entries raise `IndexError`;
   one entry indexes to a scalar and fails in the aggregation function with
   `TypeError: 'numpy.float64' object is not iterable`. No input succeeded.
   *(observed)*
2. **`_wrongdoings` is used in `disaggregate` but never imported.** Disaggregating
   in the wrong direction raises `NameError` instead of `Critical`.
3. **An unknown `method` raises `KeyError`** on the
   `_CHOOSE_DISAGGREGATION_METHOD` lookup, which happens before the frequency
   checks, so a wrong frequency direction is masked.
4. **`disaggregate` is annotated `-> Self`** but returns `None` on both paths.
5. **`aggregate` has no `else`** after the `is_regular` / `DAILY` branch, leaving
   `aggregate_func` possibly unbound. Not reachable today — `WEEKLY` has no period
   class and raises `KeyError` in `PERIOD_CLASS_FROM_FREQUENCY_RESOLUTION` first.
6. **`Literal` and `Real` are used but never imported.** Harmless at runtime
   because of `from __future__ import annotations`; `typing.get_type_hints` fails.
7. **`convert_diff` is missing from `_functional_forms`**, so unlike `convert_roc`
   and `convert_pct` it is not exported.

### Notes

1. The `Literal` annotation on `aggregate`'s `method` omits `"prod"` and
   `"geometric_mean"`, both of which `_AGGREGATION_METHOD_RESOLUTION` accepts and
   both of which work. A type checker would reject valid calls.

## `_ell_one.py`

### Bugs

1. **`lonf` returns empty series without complaint whenever the array reaching the
   solver holds a missing value.** `_lonf_for_variant` passes the data straight
   through; `nan` propagates and the returned series have `num_periods == 0`. No
   error, no warning. One mechanism, reachable two ways:
   - A missing observation inside the filtered span. *(observed:*
     `[1., 3., nan, 5., 4., 7.]` with `order=1, smooth=1.0` gives
     `trend.num_periods == 0`.*)*
   - A `span` reaching beyond the observed data, **padded with `nan` before the
     solver runs**, arriving at the same place. *(observed:* a 2019Q1-2021Q4 span
     on a series covering 2020Q1-2021Q4 returns `num_periods == 0`.*)*

   Guarding the missing-value case would cover both. A filter that hands back empty
   series is easy to miss inside a longer pipeline.
2. **Only the first variant is filtered; the rest are dropped.** *(observed:* a
   two-variant series returns `num_variants == 1`.*)* `_extrapolate.py` handles
   multiple variants correctly, so the two are worth comparing.

### Notes

1. **`FUNCTIONAL_FORMS` at the end of the module is dead.** `__all__` is built from
   `_functional_forms` well before `FUNCTIONAL_FORMS` is defined, so it cannot be
   feeding the export even by accident.
2. `Any` is imported under `TYPE_CHECKING` and never used. Confirmed by AST.
3. `lonf` is annotated `-> tuple[Self, Self]`. `Self` is meaningful only inside a
   class body; `lonf` is module-level and returns two `Series`.
4. `order` and `smooth` are positional with no defaults. `order` outside `{1, 2}`
   raises a bare `KeyError` from `_MATRIX_SETUP_DISPATCH`. *(observed: `order=3`
   gives `KeyError: 3`.)*
5. Verified: `trend + gap` reproduces the input over the resolved span; the input
   is never modified; larger `smooth` gives a smoother trend (std of the trend's
   first differences 1.55 → 0.92 → 0.62 → 0.00 for `smooth = 0.1, 1.0, 10.0,
   1000.0`); `order=1` gives flat steps, `order=2` straight sloping segments.
   *(observed)*
6. `lonf` is module-level and carries no decorator, so it cannot reach the rendered
   page — `document_namespace` collects attributes of the class. Exported as
   `dp.lonf` and visible through `help()`.

## `_extrapolate.py`

### Bugs

1. **`Self` is used in `extrapolate`'s signature but never imported**, not even
   under `TYPE_CHECKING`.
2. **`_extrapolate_data` is annotated `-> None`** but returns an array.
3. **`log=True` with a non-positive starting value** gives
   `RuntimeWarning: invalid value encountered in log` and a missing result.
   *(observed)*

### Notes

1. `ar_coeffs` accepts a bare number for a first-order process: `x.extrapolate(0.5,
   span)` behaves as `[0.5]`, via the `isinstance(ar_coeffs, Number)` guard.
   *(observed)*
2. `extrapolate` coefficient order confirmed: `[0.5, 0.25]` on `[1,2,3,4]` gives
   2.75, i.e. 0.5·4 + 0.25·3. *(observed)*
3. `extrapolate(intercept=10)` on `[1,2,3,4]` with `[0.5]` gives 12.0, 16.0.
   *(observed)*
4. `extrapolate(log=True)` with `ar_coeffs=[1.0]` and `intercept=log(2)` doubles
   each period. *(observed)*
5. Multiple variants are handled correctly, unlike `lonf` in `_ell_one.py`.
6. The functional form works: `dp.extrapolate(x, [0.5], span)` returns a new series
   and leaves `x` unchanged. *(observed)*

## `_hp.py`

**`Series.hpf` is an unimplemented stub and was left untouched by decision, so its
old docstring is still on the rendered page.** The "Docs vs code" items below are
therefore live, unlike everywhere else in this log.

### Bugs

1. **`information="one_sided"` raises `numpy.linalg.LinAlgError: Singular matrix`
   on ordinary input.** A documented, user-facing option that does not work.

   `filter_data_one_sided` loops over the periods, blanking everything after `i`
   and rerunning the two-sided filter on what remains. At `i = 0` only one
   observation is left, and the system handed to `_np.linalg.solve` can be
   singular. Whether it is depends on both series length and `smooth`:

   | quarterly periods | default `smooth` |
   | ----------------- | ---------------- |
   | 4                 | works            |
   | 5, 6, 7           | **LinAlgError**  |
   | 8 and above       | works            |

   At 6 periods: `smooth=1` works, `smooth=100` and `smooth=1600` (the quarterly
   default) both fail. *(observed)*

   Six- and seven-period quarterly series are ordinary inputs, so this is not an
   edge case; the pattern is non-monotonic, so anyone who tests 8 periods and
   concludes the option is sound will be wrong at 6; and a bare `LinAlgError` from
   inside numpy names neither the argument nor the remedy.

   **The comment above the loop asserts the opposite** — "This is not the most
   efficient way to implement the one-sided filter, but it is straightforward and
   works correctly." That claim is false and should go with the fix.

   **Latent, not live.** Nothing in the package passes `information="one_sided"`; a
   grep finds it only in two `Literal` annotations, the name of
   `filter_data_one_sided`, and the warning in the module-level `hpf` docstring.
2. **`hpf(x, span=[])` raises `wrongdoings.Error: Invalid Series object
   constructor`.** With an empty span, `_data_hpf` returns `new_start_date=None`
   alongside empty arrays, and `_SERIES_POPULATOR` in `main.py` has no populator
   for that combination. *(observed)*

### Docs vs code — live, in the `Series.hpf` stub

1. **The smoothing parameter is on the wrong term, so the docstring says `smooth`
   does the opposite of what it does.** The algorithm section reads
   λ·Σ(y−ȳ)² + Σ(Δȳ−Δȳ₋₁)², putting λ on the fit term — which would mean a larger
   `smooth` tracks the data more closely. The code puts it on the second-difference
   term: `_create_plain_filter_matrix` multiplies `K.T @ K` by `smooth` and
   `_add_eye_for_observations` adds an unweighted identity, giving
   Σ(y−ȳ)² + `smooth`·Σ(Δȳ−Δȳ₋₁)². *(observed)* On `[1., 3., 2., 5., 4., 7.]`
   quarterly, `(1600·K'K + I)ȳ = y` reproduces `hpf_trend` exactly, while the
   docstring's `(K'K + 1600·I)ȳ = y` returns values near zero.
2. The default `smooth` for monthly data is wrong by a factor of ten: the table
   says 144,000, `_AUTO_SMOOTH` computes `(10*12)**2 = 14400`.
3. The gap formula holds only for `log=False`. With `log=True` the `if log:` block
   at the end of `_data_hpf` exponentiates both components, so the returned gap is
   y / ȳ, not y − ȳ. *(observed)*
4. `information` is undocumented in the stub, though it is a real argument on
   `_data_hpf` — and see bug 1.
5. The whole reference entry hangs on `Series.hpf`, which raises
   `NotImplementedError`, so the one entry point a reader would try is the one that
   does not work. The working routines are the module-level `hpf` and the
   `hpf_trend` / `hpf_gap` methods.
6. Typos: "entier" and "unline", both in the `trend` and `gap` return descriptions.

### Notes

1. `hpf_trend` and `hpf_gap` verified under the default `information="two_sided"`:
   `hpf_trend` gives `[1.096, 2.124, 3.152, 4.181, 5.209, 6.239]`, `hpf_gap` gives
   `[-0.096, 0.876, -1.152, 0.819, -1.209, 0.761]`, they sum back to the input, and
   passing `information="two_sided"` explicitly changes nothing. *(observed)*
2. The `Series.hpf` docstring body is indented four spaces. On Python 3.11 and 3.12
   the indent survives and the whole entry renders as one code block; CPython 3.13
   strips it at compile time, which is the only reason the page looks right. This is
   the last **reference block** in `series/` written that way. Several private
   helper docstrings are also indented, but they carry no markdown and are never
   rendered, so the problem does not apply to them.

## `_indexing.py`

### Bugs

None.

### Notes

1. **The square-bracket time shift carries the same inverted sign as `shift`.**
   `x[-1]` moves the series one period later and `x[1]` one period earlier.
   *(observed)* Because `bool` is a subclass of `int`, `x[True]` is read as a time

   `[3, 2, 1]` still starting 2020Q1.
3. `reverse_columns` and `reverse_rows` are aliases of `reverse_variants` and
   `reverse_periods` — the same function objects. *(observed)*
4. All four indexing syntaxes verified: integer shift returns a new series and
   leaves the original alone; `self[dates]` and `self[dates, variants]` return
   two-dimensional arrays; assignment writes through `set_data`; the round-bracket
   call returns a new `Series`. *(observed)*

## `_jsonables.py`

### Bugs

1. **The multi-variant dead end.** The `ValueError` in `to_jsonable` instructs you
   to set `allow_multiple_variants=True`, and that flag's only effect is to raise
   `NotImplementedError` on the first line of the method. A multi-variant series
   cannot be serialized by any route.
2. **`jsonable["start"]` is read unconditionally in `from_jsonable`**, before any
   check. A round trip is safe because `to_jsonable` always writes that key, but a
   hand-built dictionary without it raises a bare `KeyError: 'start'`. Same for
   `jsonable["values"]`.

### Notes

1. The `#]` fold marker on the last line sits at 8 spaces, inside `from_jsonable`,
   while the class opened its `#[` at 4. The class has no closing marker at its own
   level.
2. `Databox` has the same typo twice in a `call_name`, in
   `databoxes/_jsonables.py`: `Databox.seres_from_jsonable` and
   `Databox.seres_from_json_file`. These set the page anchors.
3. **The two sides use different names for the same switch** — `include_frequency`
   and `include_description` when writing, `frequency_included` and
   `description_included` when reading — and nothing checks that they agree.
   Writing with one and reading with the other's default raises `KeyError`.
   *(observed)* The asymmetry is in the API; documentation cannot remove it.

## `_plotly.py`

### Bugs

1. **`plot` dispatches on substrings.** Two branches use `elif chart_type in "bar"`
   and `elif chart_type in "bar_group"` instead of `==`. Any string contained in
   `"bar"` is silently accepted as a bar chart — *(observed)* for `""`, `"b"`,
   `"a"`, `"r"`, `"ba"` and `"ar"`. The empty string is the worst case, being what
   an uninitialised variable is likely to hold.
2. **`plot_bands` mutates the caller's `update_layout` — but only when it is
   non-empty.** The method calls `.setdefault("legend_traceorder", "reversed")` on
   the caller's dictionary. The preceding `update_layout = update_layout or {}`
   replaces a *falsy* value with a fresh dictionary, so an empty dict is spared:

   | passed in | comes back as |
   | --------- | ------------- |
   | `{}` | `{}` — untouched |
   | `{"title_text": "mine"}` | `{"title_text": "mine", "legend_traceorder": "reversed"}` |

   *(observed)* The conditional half matters: anyone testing the side effect with an
   empty dict will conclude there isn't one.
3. **Dead statement in `plot`:** `trace_constructor=_line_constructor,` in the
   `"line"` branch — the trailing comma makes it a tuple assigned to a local that is
   never read.

### Notes

1. None of this file reaches the reference documentation. `__all__ = ()`, no method
   carries `@_dm.reference`, and `documark` is not imported. This is the package's
   main charting interface.
2. The real parameters of every `plot_*` method live in `_create_layout` and cannot
   be discovered from the signatures, which show only `**kwargs`. The documented
   list — `show_figure`, `return_info`, `figure`, `subplot`, `figure_title`,
   `subplot_title`, `legend`, `update_layout`, `highlight`, `vline`, `round_to` —
   is not exhaustive and will drift unless someone keeps it in step.
3. `plot_bands` sets `legend_traceorder` twice by two routes — through
   `update_layout` and through `legend_order="reversed"`.
4. `plot_bar_stack`, `plot_bar_group`, `plot_bar_overlay` and `plot_bar_relative`
   are `functools.partialmethod` objects, not `def` statements, so they cannot carry
   docstrings without a code change.
5. Band counting confirmed: `n` variants give `n // 2` bands plus a midline when `n`
   is odd. *(observed for n = 2, 3, 4, 6, 7 → 1, 2, 2, 3, 4 traces.)*
6. The `Literal` annotation for `chart_type` omits `"histogram"`, which the body
   handles and the error message advertises.

## `_temporal.py`

### Bugs

1. **`roc_from_aroc` converts in the wrong direction.** It computes
   `self.data**factor`, while every sibling divides by the factor —
   `roc_from_apct` and `pct_from_apct` both use `**(1/factor)`. It annualizes a
   second time instead of undoing the annualization. On a quarterly series growing
   10% per quarter, `aroc` gives 1.4641 and `roc_from_aroc` then returns 4.594973
   rather than recovering 1.1; applied to a raw 1.1 it returns 1.4641 where the name
   promises `1.1**(1/4) = 1.0241`. `roc_from_apct` recovers the per-period rate
   correctly from the same data. *(observed)*

   Silent and numeric: the user gets plausible values wrong by a fourth power, with
   nothing on screen to suggest it. One of the three worst findings here, with
   `_uv_filters.py` bug 1 and `_x13.py` bug 1.
2. **`cum_diff_log`'s default `initial` of 0 guarantees a zero series.**
   `_CUMULATIVE_FACTORY["diff_log"]` sets `"initial": 0`, but its forward function
   is `x_past * exp(change)`, so zero is absorbing. `cum_diff_log()` returns all
   zeros; `cum_diff_log(initial=100.)` works. It should default to 1, as `pct` and
   `roc` do. *(observed)*
3. **The annualization factor is -1 for unknown frequency.** Every annualized method
   computes `self.frequency.value or 1`, and `Frequency.UNKNOWN.value` is -1, which
   is truthy and survives the guard. Raising to the power -1 inverts the ratio rather
   than annualizing it. `INTEGER` (value 0) falls back correctly to 1. *(observed)*
4. **A bad shift string leaks a private attribute name.** `_catch_invalid_shift`
   validates only non-strings, so `diff("nonsense")` reaches the shifting machinery
   and raises `AttributeError: 'Series' object has no attribute '_shift_nonsense'`.
   Case- and whitespace-sensitive, so `"YOY"` and `"yoy "` fail the same way.
   *(observed)*
5. **`temporal_change_conversion` has a body of `pass`.** It exists only to carry
   documentation; there is no working counterpart of that name.

### Notes

1. **`_roc_from_pct` at the foot of the module is dead.** Module-level,
   underscore-prefixed, not exported, and duplicates inline what the
   `roc_from_pct` method already does. A grep finds no caller. Safe to delete.
2. Open question: `span.direction` does select between `_cumulate_forward` and
   `_cumulate_backward`, and a reversed span reports `direction == "backward"` and
   runs without error. But the one backward case tried returned a single period
   rather than a rebuilt path, and it was not possible to tell from the code whether
   the call was wrong or the path is broken.
3. **`temporal_change`'s first parameter is named `by`,** while every method built
   on it calls the same thing `shift`. Only a rename would remove the
   inconsistency.
4. Arithmetic cross-checked in both directions: `aroc` on 10%-a-quarter growth gives
   `1.1**4 = 1.4641`, `apct` gives `100*(1.1**4 - 1) = 46.41`, so the two agree and
   the `roc_from_aroc` result really is the odd one out. *(observed)*

## `_timing.py`

### Bugs

1. **The sign of a numeric `by` runs opposite to intuition.** `_shift_by_number`
   does `self.start -= by`, so `shift(-1)` moves the series later (2020Q1 → 2020Q2)
   and `shift(1)` moves it earlier. *(observed)*
2. **A non-integer number is interpolated into a method name.** `isinstance(by,
   int)` is the only thing separating the numeric route from the string route, so a
   float falls through to `getattr(self, f"_shift_{by}")` and `shift(-1.0)` raises
   `AttributeError: 'Series' object has no attribute '_shift_-1.0'`. *(observed)*
   The one a user reaches by accident — a lag computed arithmetically is a float
   more often than not, and the method named in the error could not exist under any
   spelling. A whole-number check would cost one line.
3. **An unrecognised string becomes a method name via `getattr`**, so a misspelling
   surfaces as `AttributeError: 'Series' object has no attribute
   '_shift_nonsense'`. Same leak as `_temporal.py` bug 4, same mechanism as bug 2.
4. **`ShiftType` and `Period` are used in the signatures but never imported here.**
   Both survive only on `from __future__ import annotations`. `ShiftType` is
   `int | Literal["yoy", "soy", "eopy", "tty"]`, so a type checker reading it would
   already reject the float of bug 2; nothing enforces it at runtime.
5. **`redate` on an empty series stamps a start onto nothing.** The method assigns
   `self.start` with no emptiness check, so a series whose `start` is `None` comes
   back with `start` set and no data, and its span reads backwards —
   `Series Q 2021-Q1…2020-Q4 0×1`. *(observed)* `shift` guards against this, so the
   two differ. Same shape as `main.py` note 7.

### Notes

1. `shift("eopy")` empties a series that does not already cover the previous year.
   *(observed)* Given a year to reach back into it works: `[1..8]` from 2020Q1 came
   back starting 2021Q1 as `[4, 4, 4, 4]`. *(observed)*
2. **`"yoy"` moves the series one year later, not earlier.** `_shift_yoy` calls
   `_shift_by_number(-self.frequency.value)`, the numeric form with the inverted
   sign of bug 1, so a quarterly series starting 2020Q1 comes back starting 2021Q1
   with its values untouched. *(observed)*
3. **`neutral_value` reaches `"tty"` through `**kwargs`.** `_shift_tty` in `main.py`
   writes it into the first period of each year. Left alone it is `None`, so that
   period comes back missing and, at the start of the series, is trimmed away:
   `shift("tty")` on a single year of quarterly data returns three periods starting
   a quarter later, while `shift("tty", neutral_value=0)` returns four starting
   where it began. *(observed)*
4. Neither `shift` nor `redate` carries `@_dm.reference`, so neither reaches the
   rendered page. Both are exported as `dp.shift` and `dp.redate`. *(observed)*
5. `bool` is a subclass of `int`, so `shift(True)` takes the numeric route and
   retimes by one period. *(observed)* The other side of bug 2: the same guard that
   lets a float through to the string route pulls a bool onto the numeric one.

## `_uv_filters.py`

*(See also `_apply_to_variants.py`, which the four filters run through.)*

### Bugs

1. **A gap is not merely filled — it is fed back into the recursion, and the output
   can exceed every observation in the input.** `_double_exp_smooth` writes its own
   forecast into a missing period and then updates level and slope *as though that
   forecast had been observed*. One hole in otherwise ordinary data is enough:
   `[1., 3., nan, 5., 4.]` returns `[1.0, 3.0, 5.0, 6.0, 5.9]`, where 6.0 is larger
   than anything that went in. *(observed)* The same series without the gap returns
   `[1.0, 3.0, 3.5, 5.1, 5.39]`, so the gap alone accounts for the difference.

   Silent, plausible-looking and numerically wrong, like `_temporal.py` bug 1 and
   `_x13.py` bug 1. Bug 3 below is probably the mechanism.
2. **`_double_exp_smooth` never smooths its second observation.**
   `result[second_valid_idx] = level + slope * periods_between` is algebraically
   exactly `values[second_valid_idx]`, since `slope` was just fitted to those two
   points on the line above. *(observed)* Probably intended.
3. **Mixed gap conventions inside `_double_exp_smooth`.** The initialisation divides
   the slope update by `periods_between`; the main loop uses a bare `slope` with no
   distance scaling. Gaps reach the loop through the NaN branch instead, so the two
   paths do not treat elapsed time the same way. That NaN branch is where bug 1
   happens, so fixing the convention and the feedback are likely the same work.
4. **`__all__` is built from a set,** so `tuple(...)` gives an order that is not
   stable across runs. *(observed:* four runs under `PYTHONHASHSEED` 0-3 gave four
   different orders.*)* Harmless for imports, not for generated documentation that
   lists exports in order.

### Notes

1. Stray duplicated `#]` closing `class Mixin` — two in a row at the foot of the
   class.
2. The four functional forms are generated at import time by `exec` from the
   `FUNC_STRING` template. Each copies its first argument, calls the method of the
   same name on the copy, and returns the copy. `__all__` lists these four functions
   and not the methods, so `from datapie import cum_avg` always gives the copying
   function.
3. **The argument-order trap has a concrete symptom.** `span` comes first in
   `exp_smooth`, `decay_avg` and `cum_avg`, so `x.exp_smooth(0.5)` takes the 0.5 as
   `span` and fails with `TypeError: 'float' object is not iterable` — an error that
   names neither argument. The functional forms forward `*args` untouched, so
   `dp.exp_smooth(x, 0.5)` fails identically. *(observed)* `double_exp_smooth` is
   the exception, taking `alpha, beta, span`. *(observed)*
4. Verified, all *(observed)*: `alpha=1` returns gap-free data unchanged; `alpha`
   outside `0 < alpha <= 1` raises `ValueError`; `beta` accepts 0 and 1 but not
   `-0.1` or `1.5`, so its bounds really do differ from `alpha`'s; `decay=1`
   reproduces `cum_avg` exactly and `decay=0` raises; fewer than two observations
   makes `double_exp_smooth` fall back to simple exponential smoothing; each variant
   is filtered independently; a `span` narrower than the data filters only within it
   and never shrinks the series.
5. **A leading gap can only exist in a multi-variant series.** `trim` drops a row
   only when every variant is missing, so `[[nan, 10.], [2., 20.], ...]` keeps its
   leading `nan` in the first column while a single-variant series with the same
   shape is trimmed at construction. Both `cum_avg` and `exp_smooth` leave that
   `nan` in place and start at the first number below it. *(observed)* The same
   trimming asymmetry as `_x13.py` bug 4.
6. **The `filtering` category holds `hpf` and `x13` as well as these four,** which
   is why the shared block renders under a literal name rather than the category
   name. Worth deciding whether `hpf` and `x13` belong in a category of their own.

## `_x13.py`

*Bugs are ordered so that the three that lose or corrupt data silently come first.*

### Bugs

1. **An all-negative series with a missing observation is sent to X13 unflipped,
   under a log transform. Silent.**

   `_resolve_mode` decides the mode with `_np.all((data < 0) | _np.isnan(data))`, so
   a missing value does not spoil the strict-sign test and the mode comes out
   `"mult"` with `transform=log`. The flip is decided separately by
   `flip_sign = _np.all(self.data < 0)`, where `nan < 0` is `False`, so the flip does
   not happen. The two tests treat missing values inconsistently.

   | Case | Mode | `flip_sign` | Success |
   | --- | --- | --- | --- |
   | all negative, clean | mult | `True` | `True` |
   | all negative + NaN | mult | `False` | `False` |
   | all positive + NaN | mult | `False` | `True` |
   | contains a zero | add | `False` | — |

   *(observed)* The third and fourth rows are the control: a gap alone does not
   break the run, and a zero is what actually pushes the mode to additive. In the
   failing case the spec file data begins `['-100', '-112', '-104']`, the binary
   signals `IEEE_INVALID_FLAG` and returns nothing usable. With the default
   `when_error="warning"` this warns rather than raising, so a script continues with
   an unadjusted series. One of the three worst findings here.
2. **An unrecognised `output` silently empties the series.**
   `_X11_OUTPUT_RESOLUTION.get(output, output)` passes the string through as an X13
   table name, so nothing validates it. No data comes back, the all-NaN result is
   trimmed away, and a 24-period series given `output="nonsense"` ends with
   `num_periods` 0 and `start` `None`. *(observed)* The input observations are gone.

   The call itself raises nothing; it warns. Any `IndexError` appears at the *next*
   access to the now-empty series, at whatever line reads the data, which makes it
   hard to trace back.
3. **`span` clips the input in place before X13 runs.** `self.clip(base_start,
   base_end)`. A 24-period series given `span=Span(qq(2016,1), qq(2019,4))` comes
   back with 16 periods — observations outside the span are removed from the object,
   not merely excluded from the calculation. *(observed)* Cannot be worked around
   except by copying first.
4. **`_remove_leading_trailing_nans` crashes on any variant ending in a missing
   observation.** It increments `num_trailling` (three l's) while returning
   `num_trailing`; the misspelled name is never initialised, so the call raises
   `UnboundLocalError: cannot access local variable 'num_trailling' where it is not associated with a value`.

   **Reachable through the public API.** `trim` drops a row only when *every* variant
   is missing, so a two-variant series whose first column ends in `nan` keeps that
   row through construction, and `x13()` on it raises. *(observed)* A single-variant
   series is trimmed at construction and never reaches the faulty branch, which is
   why this looks unreachable. Same trimming asymmetry as `_uv_filters.py` note 5.
5. **Unsupported frequencies fail without explanation.**
   `_X13_DATE_FORMAT_RESOLUTION` has entries for monthly and quarterly only, so a
   yearly series raises a bare `KeyError: <Frequency.YEARLY: 1>`. *(observed)*
6. **Temporary files are written to the current working directory.**
   `_write_specs_to_file` uses `_tf.NamedTemporaryFile(dir=".", ...)`. With
   `clean_up=False`, five `tmp*` files are left wherever the process is running —
   `.spc`, `.log`, `.out`, `.err` and the requested table. *(observed)* With
   `clean_up=True` the directory is left clean. *(observed)*
7. **`Callable` is used in `_x13_data`'s signature but never imported.**

### Notes

1. **The two examples in this file need an external binary; a failure here is not
   necessarily a regression.** The executable is bundled —
   `x13_runners_1_1_62/` ships `x13as_ascii` with its Fortran runtime under
   `darwin/`, `linux/` and `windows/`. Anywhere it cannot run, these two fail while
   every other doctest in `series/` passes; that pattern means the environment. The
   platform lookup `_SYSTEM_RUNNER_DISPATCH[_SYSTEM.lower()]` runs at **import
   time** and has keys for those three systems only, so on anything else the failure
   is a `KeyError` while importing `datapie`, not inside `x13`. (Read from the
   source; only Darwin was exercised.)
2. Typo left in place: `_TRANFORM_FUNCTION_DISPATCH`, missing the S. It is the real
   name of the dispatch dictionary, so fixing it means a rename.
3. `info["flip_sign"]` is `np.False_`, a numpy boolean rather than Python's `False`.
   It compares equal but reprs differently. *(observed)*
4. Five `output` aliases work: `"sf"` and
   `"seasonal_factors"` reach `d10`, `"sa"` `d11`, `"tc"` `d12`, `"irr"` `d13`.
   *(observed)*
5. `unpack_singleton`: three variants return a list of three `info` dictionaries;
   one variant returns a bare dictionary, or a list of length one with
   `unpack_singleton=False`. *(observed)*
6. `when_error="error"` raises `wrongdoings.Error: X13 failed to produce a result
   for at least one variant.` *(observed)*

## `arip.py`

### Bugs

1. **`_get_first_last_observations` returns a distance, not a count.** It returns
   `where_finite[-1] - where_finite[0]`, the gap between the first and last finite
   index, under the name `num_low_periods`. Callers use it as a divisor when
   estimating `rho` and `const`, so the growth rate and constant are computed over
   one fewer period than the name implies. *(observed)*: `[100., 200., 300.]`,
   three observations, returns 2. With a single observation the distance is 0 and
   the callers fall back to `rho=1` / `const=0`; `[nan, 100., nan, 300.]` also
   returns 2.

   The one finding here that changes the numbers, and nothing in the output
   announces it — the aggregation constraint still holds exactly (note 1), so every
   low-frequency figure is reproduced and only the shape of the path between them
   is off. That makes it invisible to the obvious check.
2. **Circular import between `arip` and `_conversions`.** Each imports the other at
   module level. This survives only on import ordering, so adding an import or
   importing a submodule directly could break the package.
3. **`disaggregate_arip` annotation is wrong on both paths.** Annotated `-> Self`,
   but returns a 2-tuple of `(Period, ndarray)`, or `(None, None)` when there is no
   start date.

### Notes

1. The aggregation constraint holds exactly for all twenty form/aggregation
   combinations — `rate`, `multiplicative`, `diff` and `additive` by `sum`, `mean`,
   `avg`, `first` and `last` — each checked against its own reconstruction.
   *(observed)*
2. A custom weights tuple must be `num_within` long, so 4 for annual-to-quarterly.
   A 12-long tuple raises `ValueError: could not broadcast input array from shape
   (12,) into shape (4,)`. *(observed)*
3. **In `disaggregate_arip`, a complete `target` for a low period displaces that
   period's own observation.** Targets `[1, 2, 3, 4]` against an annual 100.0 gave quarters summing to 10.0,
   while the two untargeted years still recovered 200.0 and 300.0. A partial target
   with only Q2 pinned to 30 kept the annual constraint. *(observed)*
4. Mutation depends on the caller. Through `disaggregate_arip` the input series is
   safe, since `iter_own_data_variants_from_until` yields copies when given an
   explicit `from_until`. Calling `disaggregate_arip_data` directly modifies the
   caller's array: `[100.0, 200.0, 300.0]` came back `[nan, 200.0, 300.0]` under a
   complete target. *(observed)* See `main.py` note 11 for the other half.
5. Error paths, all *(observed)*: an unrecognised form or aggregation name raises
   `KeyError`; a non-string, non-iterable aggregation such as `5`, `4.0` or `None`
   raises `TypeError`; a `model` that is not a 2-tuple, such as the bare string
   `"rate"`, raises `ValueError: too many values to unpack (expected 2)`; a short
   data variant or `target_data` raises `Critical`; an empty series returns
   `(None, None)`.
6. Neither function can reach the rendered page even with a decorator: both are
   module-level, and `document_namespace` collects attributes of the `Series` class.
   They are also unexported — no `__all__`, and `dp.disaggregate_arip` does not
   exist — so the only routes are `Series.disaggregate(..., method="arip")` and an
   explicit import. *(observed)*
7. `CHOOSE_AGGREGATION_FUNC` is public and referenced nowhere in the package.
   `_CHOOSE_AGGREGATION_VECTOR` is the one actually used.
8. A commented-out `indicator` parameter sits in `disaggregate_arip`'s signature,
   superseded by `target`.
9. `Self`, `Iterable` and `Real` are imported at module level rather than under
   `TYPE_CHECKING`, unlike the sibling modules.
10. `disaggregate_arip` handles multiple variants correctly: a two-variant annual
    series returns a `(12, 2)` array and each column reproduces its own annual
    figures. *(observed)*

## `main.py`

### Bugs

1. **A plain list in `values` is read as one entry per variant, not per period.**
   `_from_start_and_values` sends a non-array `values` through
   `has_variants.iter_variants`, which for a list returns
   `exhaust_then_last(anything)` in `has_variants.iter_variants` — an iterator over
   the list's *elements*. `Series(start=qq(2020,1), values=[1.0, 2.0, 3.0])` builds a
   one-period series holding 1.0. *(observed)* A tuple or a numpy array behaves as
   expected. The same rule applies through `set_data`, where a list broadcasts its
   first element across every period: `set_data(span, [7., 8., 9.])` writes 7
   everywhere. *(observed)*
2. **`get_values()` returns the first variant only.** It calls
   `_has_variants.unpack_singleton(values, unpack_singleton=...)` without passing
   `self.is_singleton`, and `has_variants.unpack_singleton` defaults that parameter
   to `True`, so the list is unpacked whatever the number of variants. A two-variant series returns one tuple and the second column is lost
   silently. `unpack_singleton=False` returns everything. *(observed)*
3. **`count_missing` returns a bool, not a count.** `_func_missing` wraps the result
   in `bool(...)`, so `np.count_nonzero` collapses to `True`/`False`, making the
   method identical to `any_missing`. Annotated `-> int`. *(observed)*
4. **`where_missing(dates)` reports the wrong periods.** The mask is computed on the
   requested data but zipped against `self.span`, so the periods returned are
   counted from the series start rather than from the request. On a series starting
   2020Q1 with a hole at 2020Q4, `where_missing(Span(qq(2020,3), qq(2021,1)))`
   returns `(qq(2020,2),)`. *(observed)* The no-argument form is correct.
5. **`shrink_num_variants(n)` with `n` equal to the current count empties every
   column.** `remove` is 0 and `self.data[:, :-remove]` is `self.data[:, :0]`,
   giving shape `(n, 0)`. *(observed)* `alter_num_variants` never reaches this case.
6. **`iter_variants` is broken twice over.** `iter_own_data_variants_from_until`
   yields the rows of `data.T`, which are one-dimensional, and `_replace_data` then
   calls `trim`, which indexes `axis=1`, so both single- and multi-variant series
   raise `numpy.exceptions.AxisError: axis 1 is out of bounds for array of dimension
   1`. *(observed)* Behind that sits a second fault: the loop runs over
   `iter_data_variants_from_until`, which is wrapped in `exhaust_then_last` and never
   terminates. Repairing the shape alone would turn the crash into an endless
   generator, so both need fixing together.
7. **`clip` fails badly at two edges.** On an empty series the comparison against a
   `None` start raises `wrongdoings.Error: Cannot handle periods of different time
   frequencies in this context`. Clipped to a span lying entirely outside the series
   it leaves an object with no data whose `start` is later than its `end` — a 2020
   series clipped to 2021Q1-2021Q2 came back with `start` 2021Q1 and `end` 2020Q4.
   *(observed)*
8. **`data_type=int` produces a series that cannot be read.** Any padding path calls
   `_np.pad(..., constant_values=_np.nan)` in `_create_expanded_data`, so a plain
   `get_data()` raises `ValueError: cannot convert float NaN to integer`.
   *(observed)*

### Notes

1. `Series.__init__` is keyword-only. `start_date=` and `dates=` are accepted as
   legacy aliases, which is why `_hp.hpf` can build its results with `start_date=`.
2. The two constructors differ over whether they copy the caller's array.
   `_from_start_and_values` ends with `values.astype(self.data_type)`, which copies
   even when the type already matches; `from_start_and_array` assigns the reshaped
   array straight through and shares it. *(observed)* both ways.
3. `Iterator` is used in three annotations and never imported; only `Iterable` and
   `Callable` are. Survives on `from __future__ import annotations`, and the IDE
   flags it on sight.
4. `_check_data_shape` is defined and called nowhere in the package.
5. `range = span` shadows the builtin inside the class body. Latent only — uses
   inside method bodies resolve to the builtin at call time.
6. `reset` erases the description, because it rebuilds the object through the
   constructor whose default is `""`. `trim` calls `reset` when every observation is
   missing, so an all-missing series loses its description too. *(observed)*
7. `empty()` keeps `start` and the description. With no rows behind it, `end`
   reports the period *before* `start` and `span` comes back backwards
   (`Span(qq(2020,1), qq(2019,4))`). *(observed)*
8. `hstack` drops descriptions; the result always has `""`. *(observed)*
9. `get_data_variant` and `get_data_variant_from_until` fall back to variant 0 when
   the index is not below the number of variants, so a mistyped index returns the
   wrong column rather than raising. Negative indices pass through to numpy and
   count from the right. *(observed)*
10. `get_data_from_until` given a reversed pair returns an empty array rather than
    raising. *(observed)*
11. `iter_own_data_variants_from_until(...)` yields views onto the series' own data,
    so writing into a yielded array changes the series; with an explicit
    `from_until` it yields fresh copies. *(observed)*
    `iter_data_variants_from_until` wraps the same iterator in `exhaust_then_last`,
    so it never stops — `list()` over it hangs. *(observed)*
12. The `_start` property (`call_name="start"`) raises `NotImplementedError` and
    exists only to carry a documentation entry. `start` is an ordinary slot
    attribute; the property never runs because the attribute shadows it, and
    assigning to the attribute retimes the series.
13. `set_start`, and assignment to `start`, do not check the frequency of the new
    period against the periods already in the series.
14. FIXME comments left in place: `__pow__` on `1 ** nan`, and the empty
    encompassing span in `_binop`.
15. **Five annotations disagree with the code.** `alter_num_variants` and `logistic`
    are `-> Self` and return `None`; `trim` is `-> None` and returns `self`;
    `get_data_and_periods` is `-> _np.ndarray` and returns a `(data, periods)`
    tuple; `_shift_eopy` is `-> Self` and returns `None`.
16. **Copy-paste slips in the operator docstrings, left in place:** `__mul__` says
    "self + other", `__rmul__` "other + self", `__truediv__` "self - other",
    `__rtruediv__` "other - self". These operators carry no decorator, so they do
    not reach the rendered page, but `help()` shows them.
